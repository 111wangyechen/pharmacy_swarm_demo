# 数字副店长上游策略多智能体完整方案

# 数字副店长上游策略多智能体方案

> 对齐现有「数字副店长工作台」交互原型，参考 `qly门店执行和复盘优化` 的文档组织方式，将“药品匹配、活动草案、库存预警”从原型页面完善为可讲述、可答辩、可开发拆解的多智能体方案。

## 1. 项目背景

医药零售门店已经沉淀了大量会员、交易、库存与活动数据，但在实际经营中仍存在三个断点：

1. **会员需求与药品推荐断点**：知道会员标签，却难以自动判断本轮活动适合推荐哪些品类。
2. **策略生成与人工审核断点**：活动配置依赖人工经验，券包、渠道、时间和门店动作缺少统一生成逻辑。
3. **活动策略与库存承接断点**：活动发布前没有充分评估库存风险，导致触达有效但门店缺货、承接不足。

本方案希望在“门店执行 Agent”和“复盘优化 Agent”之前，补齐上游策略链路：

```text
机会信号 → 会员洞察 → 药品匹配 → 活动草案 → 库存预警 → 门店执行 → 活动复盘 → 策略模板
```

## 2. 方案目标

- 把“会员标签”转化为“可运营的推荐品类”。
- 把“经营机会”转化为“可审核、可发布的活动草案”。
- 把“活动计划”提前校验为“门店库存可承接的执行方案”。
- 与现有门店执行、复盘优化模块形成完整闭环。

## 3. 核心业务场景

- 换季降温触发感冒、呼吸道、慢病关怀活动。
- 慢病会员临近复购窗口时生成复购提醒活动。
- 舆情或区域流感热点触发健康提醒与品类推荐。
- 沉睡会员召回时生成差异化券包与触达策略。
- 活动发布前识别高风险 SKU，并生成补货建议或替代品类。

## 4. 多 Agent 总体架构

本方案采用“主控 Agent + 三个核心专项 Agent + 已有下游 Agent”协同模式。

| Agent | 主要作用 | 在方案中的位置 |
| --- | --- | --- |
| 信号感知 Agent | 发现天气、舆情、季节、复购等机会信号 | 上游触发 |
| 会员洞察 Agent | 生成目标人群包与推荐理由 | 上游输入 |
| 药品匹配 Agent | 根据人群、场景、库存和合规边界推荐品类/SKU | 本方案核心 1 |
| 活动草案 Agent | 生成券包、渠道、触达时间、门店动作与审核流 | 本方案核心 2 |
| 库存预警 Agent | 预测缺货风险，生成补货建议、替代品与预约单 | 本方案核心 3 |
| 门店执行 Agent | 将已发布方案拆解为店长/店员任务 | 下游承接 |
| 复盘优化 Agent | 分析结果并沉淀模板 | 下游反馈 |

## 5. 三个核心 Agent 一句话定位

- **药品匹配 Agent**：把“会员需求与经营信号”翻译成“合规可推荐的品类清单”。
- **活动草案 Agent**：把“推荐品类与目标人群”翻译成“可审核发布的活动方案”。
- **库存预警 Agent**：把“活动需求”翻译成“门店能不能接、怎么补货、是否需要替代品”。

## 6. 方案亮点

1. **不是单点推荐，而是策略链路**：从品类匹配到活动草案，再到库存承接。
2. **不是黑箱生成，而是可解释决策**：每个推荐都有触发原因、人群依据、历史数据与合规提示。
3. **不是直接自动发布，而是保留人工审核闸门**：总部运营可调整券包、人群、时间与门店动作。
4. **不是只做活动前策略，而是接入执行和复盘闭环**：活动执行结果会回流到策略模板。

## 9. 交付口径

对老师或客户可这样概括：

> 本方案不是简单做一个活动配置页面，而是把医药零售门店的主动经营过程拆成多个可协作的智能体。系统先识别经营机会，再判断哪些会员值得触达、哪些品类适合推荐、活动券包怎样设计、门店库存能否承接，最后由门店执行并回传数据复盘。这样可以把“人工拍脑袋做活动”升级为“数据驱动、合规审核、门店可执行、结果可复用”的数字副店长闭环。

# 总体 Agent 设计

## 1. 总体架构说明

本方案围绕医药零售门店的主动经营，补齐“门店执行和复盘优化”之前的上游策略链路。系统不是只给出一句活动建议，而是将会员、药品、库存、券包、触达渠道和门店承接串联起来。

整体流程分为七个阶段：

1. **感知**：识别天气、舆情、季节、复购等机会信号。
2. **洞察**：识别目标会员、人群标签和复购窗口。
3. **匹配**：根据场景和会员需求推荐合规品类与 SKU。
4. **成案**：生成活动草案、券包、渠道、触达时间和门店动作。
5. **校验**：评估库存承接能力、缺货风险和补货需求。
6. **执行**：门店店长和店员承接活动任务。
7. **复盘**：分析效果，沉淀模板，反哺下一轮策略。

## 2. Agent 协同关系

| Agent | 输入 | 输出 | 人工参与点 |
| --- | --- | --- | --- |
| 信号感知 Agent | 天气、舆情、季节、复购周期 | 机会信号、优先级 | 是否采纳机会 |
| 会员洞察 Agent | 会员标签、消费记录、复购窗口 | 人群包、推荐原因 | 调整人群规则 |
| 药品匹配 Agent | 人群包、场景、库存、合规规则 | 推荐品类、替代品、风险提示 | 确认品类边界 |
| 活动草案 Agent | 品类结果、人群包、历史活动 | 活动草案、券包、渠道、审核流 | 审核发布、调整券包 |
| 库存预警 Agent | 活动需求、库存、销量、到货时效 | 缺货风险、补货建议、预约单 | 店长/运营确认补货 |
| 门店执行 Agent | 已发布活动、补货确认结果 | 店长任务、店员服务卡 | 任务确认与反馈 |
| 复盘优化 Agent | 触达、核销、销售、库存、执行数据 | 复盘结论、优化建议、模板 | 是否沉淀模板 |

## 3. 数据闭环关系

```text
机会信号
  → 会员洞察
  → 药品匹配
  → 活动草案
  → 库存预警
  → 门店执行
  → 活动复盘
  → 策略模板
  → 下一轮活动草案
```

关键是让每一次活动都不是一次性动作，而是持续积累策略资产：

- 药品匹配结果会影响券包和门店话术。
- 活动草案会影响库存需求预测。
- 库存预警会反向约束活动发布与推荐品类。
- 门店执行数据会成为复盘优化的输入。
- 复盘结论会沉淀为策略模板，供下一轮调用。

## 4. 前台页面与后台 Agent 的关系

前台不需要把 Agent 名称全部暴露给用户，而是以业务页面承载能力：

| 前台页面 | 背后能力 |
| --- | --- |
| 药品匹配 | 药品匹配 Agent + 会员洞察 + 合规规则 |
| 活动草案 | 活动草案 Agent + 审核流 + 券包规则 |
| 库存预警 | 库存预警 Agent + 补货建议 + 门店承接 |
| 门店执行 | 门店执行 Agent |
| 活动复盘 | 复盘优化 Agent |
| 策略模板 | 模板沉淀与再生成 |

## 5. 设计原则

1. **业务场景优先**：用户看到的是任务和结果，不是 Agent 技术名词。
2. **合规边界前置**：处方药、敏感品类、儿童用药等必须提前过滤或提示。
3. **可解释推荐**：推荐理由要能说明“为什么是这批人、为什么是这些品类”。
4. **人工审核可追溯**：活动发布、券包调整、补货确认都需要留痕。
5. **执行结果反哺策略**：复盘结果必须能影响下一轮策略。

# 药品匹配 Agent 设计

## 1. Agent 定位

药品匹配 Agent 位于“会员洞察之后、活动草案之前”，负责根据目标人群、经营场景、历史购买、库存承接和医药合规边界，生成可用于活动设计的推荐品类与 SKU 清单。

**一句话概括：** 药品匹配 Agent 的作用是把“会员需求与经营信号”翻译成“合规可推荐的品类清单”。

## 2. 解决的业务痛点

- 会员标签和药品品类割裂，运营不知道该推什么。
- 选品依赖人工经验，难以解释推荐依据。
- 活动推荐容易忽视库存、毛利和合规边界。
- 门店实际承接不足，导致活动触达后缺货或无法服务。

## 3. 输入信息

| 来源 | 输入内容 |
| --- | --- |
| 信号感知 Agent | 天气变化、季节、舆情、区域热点 |
| 会员洞察 Agent | 目标人群包、会员标签、复购周期、历史购买 |
| 商品/药品系统 | SKU、品类、适用场景、OTC/处方属性、禁忌提示 |
| 库存系统 | 门店库存、库存天数、缺货风险、替代品库存 |
| 历史活动库 | 同类活动转化率、核销率、客单价、退订反馈 |
| 合规规则库 | 处方药限制、敏感话术、儿童/慢病用药提示 |

## 4. 核心功能

1. **场景识别**：判断本轮活动属于降温、慢病复购、舆情热点、沉睡召回还是库存消化。
2. **品类召回**：从药品标签、历史购买、季节需求和关联品类中召回候选品类。
3. **推荐排序**：根据需求强度、历史转化、库存承接、毛利、合规风险计算推荐指数。
4. **合规过滤**：默认排除处方药自动营销，对敏感品类增加药师提示。
5. **替代品推荐**：当核心 SKU 库存不足时，推荐同品类或相近场景的替代品。
6. **解释生成**：输出每个推荐的业务理由和风险提示。
7. **同步草案**：将确认后的品类清单传递给活动草案 Agent。

## 5. 推荐评分规则示例

```text
推荐指数 = 场景匹配度 × 30%
        + 会员需求强度 × 25%
        + 历史转化表现 × 20%
        + 库存承接能力 × 15%
        + 毛利/经营优先级 × 10%
        - 合规风险惩罚
```

评分不是用于替代运营判断，而是帮助运营排序、解释和快速筛选。

## 6. 输出结果

| 输出对象 | 输出内容 |
| --- | --- |
| 给活动草案 Agent | 推荐品类、核心 SKU、推荐指数、券包建议 |
| 给总部运营 | 推荐理由、合规提示、替代品、毛利预估 |
| 给库存预警 Agent | 预计需求量、核心 SKU 清单、替代 SKU 清单 |
| 给门店执行 Agent | 店员话术方向、推荐边界、药师提醒 |

## 7. 典型输出示例

| 品类/SKU | 推荐指数 | 推荐原因 | 合规提示 | 替代品 |
| --- | ---: | --- | --- | --- |
| 感冒灵颗粒 | 95 | 区域降温后感冒相关购买上升，匹配呼吸敏感人群 | OTC，需药师提示 | 板蓝根颗粒 |
| 连花清瘟胶囊 | 92 | 历史同类活动核销率较高，库存覆盖较好 | OTC，避免夸大疗效 | 感冒清热颗粒 |
| 维生素 C 泡腾片 | 78 | 免疫支持需求上升，关联销售效果较好 | 普通健康推荐 | 复合维生素 |

## 8. 合规注意事项

- 不输出“治疗承诺”或“必须服用”等诊疗性质话术。
- 默认不将处方药纳入自动营销推荐。
- 对儿童、孕妇、慢病特殊人群必须增加药师咨询提醒。
- 店员侧只展示“健康关怀与购药提醒”，不替代医生诊疗。

# 活动草案 Agent 设计

## 1. Agent 定位

活动草案 Agent 位于“药品匹配之后、活动发布之前”，负责将目标人群、推荐品类、券包规则、触达渠道、时间窗口和门店动作组装成可审核、可发布、可追踪的活动方案。

**一句话概括：** 活动草案 Agent 的作用是把“推荐品类与目标人群”翻译成“可审核发布的活动方案”。

## 2. 解决的业务痛点

- 活动策划依赖人工经验，配置重复、效率低。
- 券包设计缺少毛利和转化平衡。
- 活动审核、发布和修改过程缺少结构化留痕。
- 门店动作与总部策略容易脱节。

## 3. 输入信息

| 来源 | 输入内容 |
| --- | --- |
| 药品匹配 Agent | 推荐品类、SKU、推荐指数、合规边界 |
| 会员洞察 Agent | 人群包、会员规模、推荐原因、冷却期 |
| 信号感知 Agent | 活动触发原因、时效窗口、区域影响 |
| 历史活动库 | 同类活动核销率、领券率、销售额、最佳触达时间 |
| 券系统/规则库 | 可用券模板、最低毛利率、优惠上限 |
| 门店执行 Agent | 门店动作模板、店长任务、店员话术类型 |

## 4. 核心功能

1. **活动主题生成**：根据触发原因和人群生成活动名称与主文案。
2. **券包规则建议**：生成满减券、复购券、组合券，并校验毛利率。
3. **触达渠道选择**：根据会员偏好选择企微、短信、小程序等渠道组合。
4. **触达时间建议**：结合历史打开率与活动窗口推荐发送时间。
5. **门店动作包生成**：生成库存检查、店员话术、重点会员承接动作。
6. **AI 判断依据展示**：展示触发、人群、品类、时间、库存等依据。
7. **审核状态流转**：支持草案、待审核、待开展、进行中、已完成。
8. **审计日志记录**：记录提交审核、调整券包、审核通过、发布等操作。

## 5. 活动状态机

```text
draft → pending_review → pending_launch → running → completed
  ↑           ↓
  └──── rejected
```

规则：

- 未通过毛利校验，不允许提交审核。
- 未审核通过，不允许发布。
- 发布后自动触发库存预警 Agent 进行承接校验。
- 活动完成后进入复盘优化 Agent。

## 6. 输出结果

| 输出对象 | 输出内容 |
| --- | --- |
| 给总部运营 | 活动草案、券包、触达渠道、AI 判断依据、审核日志 |
| 给库存预警 Agent | 推荐 SKU、预计触达人数、预估核销量、活动时间 |
| 给门店执行 Agent | 门店动作说明、店长任务、店员服务话术方向 |
| 给复盘优化 Agent | 活动目标、券包配置、人群口径、审核调整记录 |

## 7. 活动草案字段建议

| 字段 | 说明 |
| --- | --- |
| campaignName | 活动名称 |
| triggerSource | 触发来源：weather/chronic/sentiment/stock/manual |
| segmentId | 目标人群包 ID |
| recommendedSkus | 推荐 SKU 或品类列表 |
| couponPackage | 券包规则 |
| channels | 触达渠道 |
| scheduleAt | 触达时间 |
| storePlaybook | 门店动作说明 |
| aiEvidence | AI 判断依据 |
| status | 活动状态 |
| auditLog | 审核日志 |

## 8. 典型业务流程

1. 药品匹配 Agent 确认 5 个高匹配品类。
2. 活动草案 Agent 生成“慢病会员换季关怀活动”。
3. 系统建议企微优先、短信补充、小程序消息兜底。
4. 系统生成满减券和复购券，并校验最低毛利率。
5. 总部运营查看 AI 判断依据并调整券包。
6. 总部运营提交审核。
7. 审核通过后进入待开展。
8. 发布前触发库存预警 Agent。

# 库存预警 Agent 设计

## 1. Agent 定位

库存预警 Agent 位于“活动草案之后、门店执行之前”，负责判断活动所需商品在各门店是否具备承接能力，并给出缺货风险、补货建议、替代品和预约单。

**一句话概括：** 库存预警 Agent 的作用是把“活动需求”翻译成“门店库存能不能接、怎么补货”。

## 2. 解决的业务痛点

- 活动发布后才发现门店缺货，影响核销和会员体验。
- 补货主要靠人工判断，缺少活动需求预测。
- 不同门店库存差异大，总部难以及时发现高风险门店。
- 核心 SKU 缺货时缺少替代品策略。

## 3. 输入信息

| 来源 | 输入内容 |
| --- | --- |
| 活动草案 Agent | 活动时间、推荐 SKU、预计触达人数、预计核销率 |
| 药品匹配 Agent | 核心 SKU、替代品、合规边界 |
| 库存系统 | 当前库存、库存天数、在途库存、近效期库存 |
| POS/交易系统 | 近 7/14/30 日日均销量、趋势变化 |
| 供应链系统 | 到货时效、供应商、最小起订量、预约单状态 |
| 门店执行 Agent | 门店承接优先级、店长确认状态 |

## 4. 核心功能

1. **需求预测**：根据触达人数、预估核销率和历史销量推算活动需求。
2. **库存天数计算**：评估当前库存可支撑多少天。
3. **风险分级**：按缺货概率分为高、中、低风险。
4. **补货建议生成**：给出 SKU 级建议补货量和原因。
5. **替代品建议**：核心 SKU 不足时推荐替代品类。
6. **预约单生成**：生成供应链预约单摘要。
7. **门店同步**：将补货确认结果同步到门店执行 Agent。
8. **异常上报**：当库存承接率不足时提醒运营调整活动范围或品类。

## 5. 风险判断规则示例

```text
活动预计需求 = 触达人数 × 预计核销率 × 单人购买件数
安全库存 = 近 7 日日均销量 × 安全天数
建议补货量 = max(活动预计需求 + 安全库存 - 当前库存 - 在途库存, 0)
库存天数 = 当前库存 / 近 7 日日均销量
```

风险分级：

| 风险等级 | 判断逻辑 |
| --- | --- |
| 高风险 | 库存天数 < 2 天，或活动需求缺口 > 50% |
| 中风险 | 库存天数 2-4 天，或活动需求缺口 20%-50% |
| 低风险 | 库存天数 > 4 天，且活动需求缺口 < 20% |

## 6. 输出结果

| 输出对象 | 输出内容 |
| --- | --- |
| 给总部运营 | 高风险 SKU、受影响门店、库存承接率、调整建议 |
| 给供应链/采购 | 补货建议、预约单、到货时效 |
| 给门店执行 Agent | 店长补货确认任务、库存风险提示 |
| 给药品匹配 Agent | 缺货 SKU 与替代品反馈 |
| 给复盘优化 Agent | 活动前库存风险、实际缺货、补货及时率 |

## 7. 典型输出示例

| SKU | 当前库存天数 | 建议量 | 风险原因 | 到货时效 |
| --- | ---: | ---: | --- | --- |
| 感冒灵颗粒 | 1.5 天 | 300 盒 | 活动需求高，库存天数过低 | 24-48 小时 |
| 连花清瘟胶囊 | 2.1 天 | 280 盒 | 高匹配品类，部分门店缺货 | 24-48 小时 |
| 板蓝根颗粒 | 2.8 天 | 220 盒 | 库存偏低，可作为替代品 | 24-48 小时 |

## 8. 活动约束建议

当库存承接不足时，库存预警 Agent 不只是提示补货，还可以反向给出策略建议：

- 缩小活动门店范围，只覆盖库存充足门店。
- 延迟活动发布时间，等待补货到位。
- 调整推荐品类，优先选择替代 SKU。
- 降低触达规模，分批推送。
- 对高风险门店增加店长确认任务。

# 业务闭环流程说明

## 1. 业务场景入口

本方案可以从以下入口触发：

- 天气降温：未来 72 小时降温明显。
- 慢病复购：会员接近复购窗口但尚未购买。
- 舆情热点：区域流感、过敏、呼吸道相关搜索或舆情升温。
- 沉睡召回：高价值会员长时间未购药。
- 库存经营：近效期商品或库存压力需要运营消化。

## 2. 端到端流程

```text
1. 信号感知 Agent 发现机会
2. 会员洞察 Agent 生成目标人群包
3. 药品匹配 Agent 推荐合规品类与 SKU
4. 活动草案 Agent 生成活动方案与券包
5. 总部运营审核并调整
6. 库存预警 Agent 校验库存承接能力
7. 门店执行 Agent 拆解店长和店员任务
8. 门店完成服务、核销和反馈
9. 复盘优化 Agent 分析效果
10. 成功经验沉淀为策略模板
```

## 3. 用户侧体验

总部运营看到的是一个“从机会到活动”的工作台：

```text
工作台 → 药品匹配 → 活动草案 → 库存预警 → 门店执行 → 活动复盘 → 策略模板
```

门店店长看到的是“今天要做什么”：

```text
今日任务 → 补货确认 → 重点会员承接 → 异常反馈
```

店员看到的是“面对这个会员怎么服务”：

```text
会员服务卡 → 推荐话术 → 可用券 → 风险提示 → 履约反馈
```

## 4. 为什么需要药品匹配、活动草案和库存预警三段

如果只有药品匹配，系统只能回答“推什么”。

如果只有活动草案，系统只能回答“怎么推”。

如果没有库存预警，即使活动设计合理，也可能在线下门店承接时失败。

因此这三个 Agent 共同组成活动发布前的核心策略链路：

```text
推什么 → 怎么推 → 能不能接
```

## 5. 与门店执行和复盘优化的关系

- 药品匹配、活动草案、库存预警负责活动前策略生成和校验。
- 门店执行负责把策略转成任务和话术。
- 复盘优化负责判断策略与执行是否有效。

它们共同形成一个完整业务闭环：

```text
策略生成 → 库存校验 → 门店执行 → 数据回传 → 复盘优化 → 模板沉淀
```

# MVP 落地计划

## 1. MVP 范围

本轮 MVP 重点验证“药品匹配 → 活动草案 → 库存预警”的策略链路是否可讲通、可操作、可演示。

### 必做

- 药品匹配页：推荐品类、推荐指数、推荐理由、合规提示、加入草案。
- 活动草案页：活动字段、券包规则、AI 判断依据、提交审核、审核通过、发布。
- 库存预警页：高风险 SKU、补货建议、预约单摘要、一键确认补货。
- 与门店执行、活动复盘、策略模板形成跳转链路。

### 暂不做

- 真实 CRM、ERP、库存系统接口。
- 真实短信、企微、小程序发送。
- 复杂算法训练平台。
- 完整 RBAC 权限。

## 2. 关键验收指标

| 模块 | 验收点 |
| --- | --- |
| 药品匹配 | 推荐列表至少包含推荐指数、原因、合规提示、替代品 |
| 活动草案 | 未通过毛利校验不能提交审核；未审核不能发布 |
| 库存预警 | 每个高风险 SKU 都能看到建议量、风险原因和到货时效 |
| 闭环跳转 | 药品匹配可同步草案，活动发布可进入库存预警，补货确认可同步门店执行 |
| 复盘沉淀 | 活动完成后可保存策略模板 |

## 3. 里程碑建议

| 阶段 | 产出 |
| --- | --- |
| M1 | 完成三 Agent 方案文档和流程图 |
| M2 | 完成药品匹配与活动草案前端交互 |
| M3 | 完成库存预警、补货确认和活动发布状态流转 |
| M4 | 串联门店执行与复盘优化，完成答辩演示脚本 |

## 4. 演示脚本

1. 从首页进入药品匹配 Agent。
2. 查看“换季降温 + 慢病复购”条件下的推荐品类。
3. 点击加入草案并同步到活动草案 Agent。
4. 查看活动名称、目标人群、券包、渠道和 AI 判断依据。
5. 调整券包，提交审核，模拟审核通过。
6. 确认发布后进入库存预警 Agent。
7. 查看高风险 SKU 和补货建议。
8. 生成预约单，一键确认补货。
9. 说明后续进入门店执行和复盘优化，形成闭环。

## 5. 方案评价口径

本方案的价值不在于“页面做得多”，而在于完整表达了医药零售门店主动经营的关键逻辑：

```text
识别谁需要 → 判断推什么 → 生成怎么推 → 校验能不能接 → 推动门店执行 → 复盘沉淀模板
```
